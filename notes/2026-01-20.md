I just spent 30 minutes talking to Google search about how kubernetes and docker works.

1. I knew that containers were lighter weight than a virtual machine and that they shared the operating system of their host but I didn't know what that really meant. I didn't understand how a Linux container could share the host kernel of a windows machine. The LLM told me that that is what Docker, in part, accomplishes. It provides the interface for a linux container on a windows machine. I then wondered about all the other combinations, A on B, where A or B can be MAc, Linux, or Windows. See figure below. In essence, Mac containers don't exist, and windows containers can only on windows. Linux containers run on all 3 major OS's. This means Docker the org. only has to account for these 4 scenarios, 2 of which are "native" because the host is the same OS as the container. This made more sense to me once I realized Docker has to "hardcode" these scenarios into their engine.
2. I then asked, not thinking really, how different Linux distros run containers from different distros. Since distros are all still linux, the system calls mostly work the same, what is different is package management and lbiraries. Docker does require a minimum version of the Linux kernel however.
3. Today I learned that the Kubernetes API is not ran off-site but is instead a process running in the Kube control plane. I always wondered why the apiVersions at the top of definitions were written the way they were, that's why I assumed they were URLs and therefore the API had to be ran off-site. The kube controller or helm controller or flux controllers are the things that know how to build the resources that are defined. The apiVersion is just another namespace.
4. I also learned what etcd. It's the storage for the kube-controller. It's just a key-value storage.
5. It also became a lot clear that kubernetes is not a strictly-defined orchestrator as orchestrators technically just have a defined workflow. Kubernetes defines an end-state for a cluster and uses several independent processes to get there that are not always sequential. It also does not aim to be a PAAS, it tries to be as flexible as possible, as well as pluggable. It can run redis or mysql but it doesn't provides its own cache or database for apps. It does not replace CI/CD, even if a CI/CD workflow uses kubernetes to deploy.
6. This is what the LLM spit out: How they interact (Literal Flow)
If you want to run 3 copies of an application, here is the sequence:\n
User to API: You send a Deployment manifest (specifying 3 replicas) to the API Server.\n
API to etcd: The API Server validates the YAML and writes the record into etcd.\n
etcd to Controller: The Deployment Controller has a "watch" on Deployment objects. etcd notifies the controller that a new record exists.\n
Controller Logic: The controller reads the record and sees "Replicas: 3". It then asks the API Server, "How many Pods exist with this label?" The API returns 0.\n
Controller to API: The controller sends 3 separate requests to the API Server: "Create Pod 1," "Create Pod 2," and "Create Pod 3."\n
API to Scheduler: The Scheduler (another controller) sees those new Pods have no "node" assigned. It picks a node and updates the Pod records in etcd.\n
Kubelet Action: The Kubelet on the physical server is watching for Pods assigned to its specific node name. It sees the update and finally commands the local Container Runtime (like Docker or containerd) to start the processes.\n
In summary: etcd holds the records, and Controllers are the active code that reads those records and issues the next set of instructions to make those records a reality.\n\n
